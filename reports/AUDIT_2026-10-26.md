## 2. REAL BUGS FOUND (2)

### BUG 1 — `GoalCategory` validation crashes the whole cycle on a bad string
**Severity: medium (availability/robustness).** Evidence:
`sonic_data/self_coder_candidates/263628cb…json` (2026-10-25T09:59:35):

```
status: failed
error:  'ensure logger module has no obvious defect' is not a valid GoalCategory
report: Cycle 1: bug_fix → Outcome: error → Tree: rolled_back
```

`goal_director.py:215` does `GoalCategory(category) if isinstance(category, str)`.
A `StrEnum` lookup raises a raw `ValueError` for any string that is not one of the
five literal values. Reproduced directly:

```
category='ensure logger module has no obvious defect': CRASH ValueError
category='':            CRASH ValueError
category='BUG_FIX':     CRASH ValueError   # case-sensitive
category='bugfix':      CRASH ValueError   # underscore required
```

Impact: one malformed/aliased category string aborts an entire evolution cycle
and writes a `failed` candidate. A `category` arriving from an operator field, an
LLM proposal, or a persisted row with an alias will kill the cycle instead of
degrading gracefully.

**Suggested fix (small):** normalise + fall back instead of raising, e.g.
`cat = GoalCategory(str(category).strip().lower())` inside a `try/except ValueError`
defaulting to `LOGIC_IMPROVEMENT`, and log `goal_category_normalized`. Keep an
explicit strict mode for tests if desired.

### BUG 2 — `_repair_hunk_counts` cannot fix a diff with no `---`/`+++` file header
**Severity: low (patch-apply success rate).** The synthesizer repairs wrong hunk
*counts*, but a bare `@@ -14,6 +15,7 @@` block with **no preceding `--- a/…` /
`+++ b/…` header** still fails git apply with `patch fragment without header at
line 13` — one of the observed candidate failures (2026-10-25T06:53:17,
`apps/cli/sonic_cli/developer_agent.py`). Verified:

```
input : '@@ -14,6 +15,7 @@\n context\n+added\n more context\n'
output: '@@ -14,2 +15,3 @@\n context\n+added\n more context\n'   # counts fixed,
                                                                  # but still no file header
```

The historical "corrupt patch" cluster (12 candidates, 2026-10-23 → 10-25) is
mostly the *count* problem my earlier fix (`9d310e9`) addresses; the remaining
"without header" and "patch does not apply (context mismatch)" cases are a
different class. Note the newest runs after the fix (10:22–10:48) show
`patch failed: …` (context mismatch) rather than `corrupt patch`, and 10:58
produced the first **verified** candidate — so the earlier fix helped; this is a
residual robustness gap, not a regression.

**Suggested fix (small):** when a hunk block has no file header and the target
path is known, synthesise the `--- a/<path>` / `+++ b/<path>` header from the
candidate's `target_file` before the first `@@`.

## 3. Security — strong, no critical hole

- **Auth coverage:** only 7 routes lack an auth dependency and all are expected
  (`/login`, `/dev-token`, Google OAuth config/login/callback, `/health`,
  `/health/detailed`). `POST /dev-token` is hard-gated to
  `app_env == "development"` and can never elevate to `SUPER_ADMIN` /
  `TENANT_ADMIN`.
- **Sealed safety envelope:** `SealedActionPolicy` present; the seal hash is
  recomputed and compared on every `evaluate()`; tamper → fail-closed DENY.
  Frozen egress snapshot prevents widening via module-level mutation.
- **Egress filter:** blocks RFC1918, loopback, cloud metadata `169.254.169.254`,
  IPv4-mapped IPv6 (`::ffff:0:0/96`) and NAT64 — the mapped-IPv6 SSRF bypass is
  closed.
- **Docker posture:** `/var/run/docker.sock` is **not** mounted in either compose
  file (prior audit finding fixed). `docker-compose.prod.yml` injects secrets via
  `${VAR:?…}` and declares `deploy.resources.limits` for both services.
- **Secrets hygiene:** no hardcoded credentials in source; `.env`, `*.db`,
  `sonic_data/`, `*.pt` are gitignored and untracked. `git ls-files` confirms
  zero `sonic_data`/`*.db` entries tracked.
- **Fail-closed provider:** `HeadlessComputerProvider` returns exit code `126`
  and a BLOCKED result when host execution is disabled — it never spawns a host
  subprocess.

### Minor security note
`sonic/safety/sealed.py:127` swallows an exception (`except Exception: pass`)
while capturing the scope-checker rules used for tamper evidence. If that capture
fails, the seal silently records **empty** rules rather than failing closed. Low
risk (the seal still covers the frozen egress snapshot and config fields), but
worth logging instead of `pass` so a silent degradation is visible.

## 4. Boss / subagent visibility — the operator's original concern: WIRED ✅

Verified in code **and** by 39 passing tests
(`test_worker_detail_api_contract`, `test_boss_worker_visibility`,
`test_worker_activity_end_to_end`, `test_workstation_agent_activity`).

- `SubMissionResult` carries a **stable, run-unique** `agent_uid`
  (e.g. `worker-1-a1b2c3`) in addition to the positional `agent_id` — so a worker
  can be addressed across a persisted session, not just within one Boss run.
- `GET /workstation/agents/{agent_uid}` returns the worker drill-down; the
  workstation route streams `sub_dispatch` / `sub_step` / `sub_report` /
  `phase_complete` / `boss_report` events each carrying
  `sub_agent_id` / `sub_agent_uid`.
- `GET /workstation/agents/{agent_uid}` + `POST …/message` let the operator click
  a worker and message it (`coordinator_inbox`).
- Background liveness is surfaced (`dispatched_count` vs `planned_count`) so the
  UI cannot report a phantom completion.

This directly addresses the reported complaint ("agent ko id/name hona chahiye,
click karke dekha ja sake ki kya kar raha hai").
